# 技能系统架构设计分析

## 当前实现：继承模式

### 继承层次结构

```
GameplayAbility (基类)
├── ActiveAbility (主动技能)
│   ├── ComboAbility (连击技能)
│   ├── ChannelingAbility (引导技能)
│   ├── ProjectileAbility (投射物技能)
│   └── MagicFieldAbility (魔法场技能)
└── PassiveAbility (被动技能)
```

### 继承模式的优点

1. **类型安全**：编译时类型检查，IDE 支持好
2. **代码复用**：公共逻辑在基类中实现，子类继承
3. **概念清晰**：每个技能类型有明确的类定义
4. **易于理解**：继承关系直观，符合面向对象思维

### 继承模式的问题

#### 1. **组合爆炸问题（Combinatorial Explosion）**

**问题场景**：
- 需要一个"连击+投射物"技能（ComboProjectileAbility）
- 需要一个"引导+魔法场"技能（ChannelingMagicFieldAbility）
- 需要一个"连击+引导"技能（ComboChannelingAbility）

**当前方案**：需要创建新的类，导致类数量爆炸
```
ComboProjectileAbility
ComboChannelingAbility
ChannelingProjectileAbility
ChannelingMagicFieldAbility
ComboChannelingProjectileAbility
... (N种组合 = 2^N 个类)
```

#### 2. **多重继承不可行**

GDScript 不支持多重继承，无法同时继承 `ComboAbility` 和 `ProjectileAbility`。

#### 3. **职责边界模糊**

某些技能类型（如 `ComboAbility`）更像是"行为修饰器"而非独立技能类型：
- `ComboAbility` 管理连击逻辑，但实际效果由子技能提供
- `ChannelingAbility` 管理生命周期，但效果仍由基类提供

#### 4. **扩展性受限**

添加新技能类型需要：
- 创建新类
- 理解整个继承层次
- 可能需要在多个基类中修改代码

#### 5. **代码重复**

某些技能类型需要重写大量方法，导致代码重复：
```gdscript
# ProjectileAbility 和 MagicFieldAbility 都需要：
# - 重写 _on_cast()
# - 实现生成逻辑
# - 管理生命周期
```

## 替代方案：组合模式（Component-Based）

### 核心思想

将技能行为拆分为独立的"行为组件"（Behavior Component），技能通过组合这些组件来实现功能。

### 设计示例

```gdscript
# 基础技能类（只包含核心数据）
class_name GameplayAbility extends Resource
    @export var ability_id: StringName
    @export var statuses: Array[GameplayStatusData] = []
    @export var effects: Array[GameplayEffect] = []
    # ... 其他基础属性

# 行为组件接口
class_name AbilityBehavior extends RefCounted
    func can_cast(ability: GameplayAbility, context: AbilityContext) -> bool: pass
    func commit_cast(ability: GameplayAbility, context: AbilityContext) -> bool: pass
    func on_cast(ability: GameplayAbility, context: AbilityContext) -> void: pass
    func update(ability: GameplayAbility, delta: float) -> void: pass

# 具体行为组件
class_name CooldownBehavior extends AbilityBehavior
    @export var cooldown_duration: float = 0.0
    # 实现冷却逻辑

class_name CostBehavior extends AbilityBehavior
    @export var costs: Array[AbilityCostBase] = []
    # 实现消耗逻辑

class_name ComboBehavior extends AbilityBehavior
    @export var combo_abilities: Array[GameplayAbility] = []
    # 实现连击逻辑

class_name ProjectileBehavior extends AbilityBehavior
    @export var projectile_data: ProjectileData = null
    # 实现投射物逻辑

class_name ChannelingBehavior extends AbilityBehavior
    @export var channeling_mode: ChannelingMode
    # 实现引导逻辑

# 技能通过组合行为组件
class_name ActiveAbility extends GameplayAbility
    @export var behaviors: Array[AbilityBehavior] = []
    
    func _can_cast(context: AbilityContext) -> bool:
        for behavior in behaviors:
            if not behavior.can_cast(self, context):
                return false
        return true
    
    func _on_cast(context: AbilityContext) -> void:
        for behavior in behaviors:
            behavior.on_cast(self, context)
```

### 组合模式的优点

1. **灵活组合**：可以任意组合行为组件
   - 连击+投射物：`[ComboBehavior, ProjectileBehavior]`
   - 引导+魔法场：`[ChannelingBehavior, MagicFieldBehavior]`
   - 连击+引导+投射物：`[ComboBehavior, ChannelingBehavior, ProjectileBehavior]`

2. **避免组合爆炸**：不需要为每种组合创建新类

3. **职责清晰**：每个行为组件只负责一个功能

4. **易于扩展**：添加新行为只需创建新组件，无需修改现有代码

5. **代码复用**：行为组件可以在不同技能间复用

6. **数据驱动**：可以在编辑器中配置行为组合

### 组合模式的缺点

1. **类型安全降低**：运行时组合，编译时检查较少

2. **性能开销**：需要遍历行为组件数组（但通常可忽略）

3. **调试困难**：行为分散在多个组件中，调用栈更深

4. **学习曲线**：需要理解组件系统，对新手不友好

5. **组件间通信**：组件之间可能需要共享状态，增加复杂度

## 混合方案：继承 + 组合

### 设计思路

保留继承用于**核心技能类型**（Active/Passive），使用组合用于**行为特性**（Combo/Channeling/Projectile）。

### 设计示例

```gdscript
# 核心技能类型（继承）
class_name ActiveAbility extends GameplayAbility
    # 核心属性：冷却、消耗、前摇等
    @export var cooldown_duration: float = 0.0
    @export var costs: Array[AbilityCostBase] = []
    @export var cast_point_time: float = 0.5

# 行为特性（组合）
class_name AbilityFeature extends RefCounted
    func can_cast(ability: ActiveAbility, context: AbilityContext) -> bool: return true
    func commit_cast(ability: ActiveAbility, context: AbilityContext) -> bool: return true
    func on_cast(ability: ActiveAbility, context: AbilityContext) -> void: pass
    func update(ability: ActiveAbility, delta: float) -> void: pass

# 具体特性
class_name ComboFeature extends AbilityFeature
    @export var combo_abilities: Array[ActiveAbility] = []

class_name ProjectileFeature extends AbilityFeature
    @export var projectile_data: ProjectileData = null

class_name ChannelingFeature extends AbilityFeature
    @export var channeling_mode: ChannelingMode

# ActiveAbility 支持特性组合
class_name ActiveAbility extends GameplayAbility
    @export var features: Array[AbilityFeature] = []
    
    func _can_cast(context: AbilityContext) -> bool:
        # 基类检查
        if not _check_base_conditions(context):
            return false
        # 特性检查
        for feature in features:
            if not feature.can_cast(self, context):
                return false
        return true
    
    func _on_cast(context: AbilityContext) -> void:
        # 基类逻辑
        _apply_base_effects(context)
        # 特性逻辑
        for feature in features:
            feature.on_cast(self, context)
```

### 混合方案的优点

1. **平衡灵活性和类型安全**：核心类型用继承，特性用组合

2. **向后兼容**：现有技能类型可以逐步迁移

3. **渐进式重构**：可以先迁移部分特性，保留现有类

4. **编辑器友好**：可以在编辑器中配置特性组合

## 推荐方案

### 方案 A：保持当前继承模式（适合当前阶段）

**适用场景**：
- 技能类型相对固定，组合需求少
- 团队规模小，维护成本可控
- 项目处于快速迭代阶段

**建议**：
- 保持当前设计
- 为常见组合创建专门的类（如 `ComboProjectileAbility`）
- 通过文档说明何时需要创建新类

### 方案 B：混合方案（推荐，长期方向）

**适用场景**：
- 需要频繁组合不同技能特性
- 希望提高灵活性和可扩展性
- 有时间和资源进行重构

**实施步骤**：
1. **第一阶段**：引入 `AbilityFeature` 系统，作为可选扩展
2. **第二阶段**：将 `ComboAbility`、`ProjectileAbility` 等迁移为 `Feature`
3. **第三阶段**：逐步将现有技能迁移到特性系统
4. **第四阶段**：保留 `ActiveAbility` 和 `PassiveAbility` 作为核心类型

**设计要点**：
- `ActiveAbility` 和 `PassiveAbility` 保留为继承（核心类型）
- `Combo`、`Channeling`、`Projectile`、`MagicField` 改为 `Feature`（可组合特性）
- 提供迁移工具和文档

### 方案 C：完全组合模式（激进，不推荐）

**适用场景**：
- 需要极高的灵活性
- 愿意承担更高的复杂度和学习成本

**缺点**：
- 类型安全降低
- 调试困难
- 学习曲线陡峭

---

## 具体建议

### 短期（当前阶段）

1. **保持当前继承模式**
   - 当前设计已经足够灵活
   - 避免过早优化

2. **为常见组合创建专门类**
   - 如果确实需要"连击+投射物"，创建 `ComboProjectileAbility`
   - 通过文档说明何时需要新类

3. **优化现有设计**
   - 提取公共逻辑到基类
   - 减少代码重复

### 中期（6-12个月）

1. **引入特性系统（Feature System）**
   - 作为可选扩展，不影响现有代码
   - 新技能可以使用特性系统

2. **逐步迁移**
   - 将 `ComboAbility` 迁移为 `ComboFeature`
   - 将 `ProjectileAbility` 迁移为 `ProjectileFeature`

### 长期（1-2年）

1. **完全采用混合方案**
   - 核心类型用继承（Active/Passive）
   - 特性用组合（Combo/Channeling/Projectile/MagicField）

2. **提供迁移工具**
   - 自动将旧技能转换为新格式
   - 保持向后兼容

---

## 结论

**当前继承模式是合理的**，但**混合方案更适合长期发展**。

### 当前设计的合理性

1. ✅ 技能类型相对固定（Active/Passive）
2. ✅ 组合需求较少（大多数技能是单一类型）
3. ✅ 类型安全，IDE 支持好
4. ✅ 代码清晰，易于理解

### 何时考虑重构

1. ⚠️ 频繁需要组合不同技能特性
2. ⚠️ 技能类型数量快速增长
3. ⚠️ 维护成本显著增加
4. ⚠️ 用户反馈需要更高灵活性

### 最终建议

**保持当前设计，但为未来重构做准备**：
1. 提取公共逻辑，减少代码重复
2. 设计清晰的接口，便于未来迁移
3. 在文档中说明设计思路和扩展方式
4. 当组合需求增加时，逐步引入特性系统
