# 完全组合模式设计分析

## 当前架构 vs 完全组合模式

### 当前架构（混合模式）

```
GameplayAbility (基类)
├── ActiveAbility (主动技能)
│   └── features: [ComboFeature, ProjectileFeature, ...]
└── PassiveAbility (被动技能)
    └── features: [ConditionalFeature, ...]
```

**特点**：
- 核心类型用继承（ActiveAbility、PassiveAbility）
- 行为特性用组合（ComboFeature、ProjectileFeature等）
- 冷却、消耗内嵌在 ActiveAbility 中

### 完全组合模式（激进方案）

```
GameplayAbility (基类，仅包含基础数据)
└── features: [
    ActiveFeature,        // 主动技能特性
    CooldownFeature,     // 冷却特性
    CostFeature,         // 消耗特性
    ComboFeature,        // 连击特性
    ProjectileFeature,   // 投射物特性
    ...
]
```

**特点**：
- 所有行为都用特性实现
- 技能只是一个容器，通过组合特性实现所有功能
- 架构完全扁平，无继承层次

---

## 设计提案

### 方案 A：完全组合模式（激进）

#### 核心设计

```gdscript
# 基础技能类（仅包含数据，无行为）
class_name GameplayAbility extends Resource
    @export var ability_id: StringName
    @export var ability_name: String
    @export var statuses: Array[GameplayStatusData] = []
    @export var features: Array[AbilityFeature] = []  # 所有行为都通过特性实现

# 主动技能特性
class_name ActiveFeature extends AbilityFeature
    # 提供主动技能的施放流程钩子
    func can_cast(...) -> bool
    func commit_cast(...) -> bool
    func on_cast(...) -> void

# 被动技能特性
class_name PassiveFeature extends AbilityFeature
    # 提供被动技能的生命周期钩子
    func on_learned(...) -> void
    func on_forgotten(...) -> void

# 冷却特性
class_name CooldownFeature extends AbilityFeature
    @export var cooldown_duration: float = 0.0
    func can_cast(...) -> bool  # 检查冷却
    func commit_cast(...) -> bool  # 开始冷却

# 消耗特性
class_name CostFeature extends AbilityFeature
    @export var costs: Array[AbilityCostBase] = []
    func can_cast(...) -> bool  # 检查资源
    func commit_cast(...) -> bool  # 支付消耗
```

#### 使用示例

```gdscript
# 主动技能 = ActiveFeature + CooldownFeature + CostFeature
var active_ability = GameplayAbility.new()
active_ability.features = [
    ActiveFeature.new(),
    CooldownFeature.new(),
    CostFeature.new(),
    ProjectileFeature.new()
]

# 被动技能 = PassiveFeature（无冷却、无消耗）
var passive_ability = GameplayAbility.new()
passive_ability.features = [
    PassiveFeature.new()
]

# 切换技能 = ActiveFeature + CooldownFeature（无消耗）
var toggle_ability = GameplayAbility.new()
toggle_ability.features = [
    ActiveFeature.new(),
    CooldownFeature.new(),
    ChannelingFeature.new()
]
```

#### 优点

1. **极致灵活**：可以任意组合，如"被动技能+冷却时间"、"主动技能+无消耗"
2. **架构扁平**：无继承层次，所有技能都是 `GameplayAbility`
3. **数据驱动**：完全通过配置实现，无需创建新类
4. **易于扩展**：添加新行为只需创建新特性，无需修改现有代码
5. **统一接口**：所有技能都通过 `features` 数组管理

#### 缺点

1. **类型安全降低**：编译时无法保证技能类型正确（如被动技能不应该有冷却）
2. **调试困难**：行为分散在多个特性中，调用栈更深
3. **学习曲线陡峭**：需要理解特性系统才能使用
4. **性能开销**：需要遍历特性数组，虽然通常可忽略
5. **配置复杂**：需要配置多个特性才能实现基本功能
6. **可能过度设计**：对于简单技能，特性系统可能过于复杂

### 方案 B：渐进式组合（推荐）

#### 核心设计

保持当前混合模式，但将冷却和消耗也做成可选特性：

```gdscript
# ActiveAbility 保留，但冷却和消耗变为可选特性
class_name ActiveAbility extends GameplayAbility
    # 保留基础属性（向后兼容）
    @export var cooldown_duration: float = 0.0
    @export var costs: Array[AbilityCostBase] = []
    
    # 特性系统（新）
    @export var features: Array[AbilityFeature] = []
    
    # 如果配置了 CooldownFeature，使用特性；否则使用内嵌属性
    func get_cooldown_duration() -> float:
        for feature in features:
            if feature is CooldownFeature:
                return (feature as CooldownFeature).cooldown_duration
        return cooldown_duration  # 向后兼容
```

#### 优点

1. **向后兼容**：现有技能无需修改
2. **渐进迁移**：可以逐步将冷却/消耗迁移到特性
3. **灵活性**：可以选择使用特性或内嵌属性
4. **类型安全**：ActiveAbility 仍然存在，类型检查仍然有效

#### 缺点

1. **两套系统并存**：可能造成混淆
2. **迁移成本**：需要逐步迁移现有技能

### 方案 C：完全组合模式 + 类型标记（折中）

#### 核心设计

```gdscript
# 基础技能类
class_name GameplayAbility extends Resource
    @export var ability_id: StringName
    @export var features: Array[AbilityFeature] = []
    
    # 类型标记（用于类型检查和编辑器显示）
    enum AbilityType { ACTIVE, PASSIVE, TOGGLE }
    @export var ability_type: AbilityType = AbilityType.ACTIVE
    
    # 辅助方法：检查是否包含特定特性
    func has_feature(feature_class: String) -> bool:
        for feature in features:
            if feature.get_script().get_path().get_file().get_basename() == feature_class:
                return true
        return false

# 使用示例
var ability = GameplayAbility.new()
ability.ability_type = GameplayAbility.AbilityType.ACTIVE
ability.features = [
    ActiveFeature.new(),
    CooldownFeature.new(),
    CostFeature.new()
]

# 类型检查
if ability.ability_type == GameplayAbility.AbilityType.ACTIVE:
    # 确保有 ActiveFeature
    assert(ability.has_feature("ActiveFeature"))
```

#### 优点

1. **灵活性**：完全组合模式的所有优点
2. **类型标记**：通过枚举提供类型信息
3. **运行时检查**：可以验证特性组合是否合理

#### 缺点

1. **运行时检查**：类型安全仍然是运行时的，不是编译时
2. **配置复杂**：需要同时配置类型和特性

## 推荐方案

### 短期（当前阶段）

**保持混合模式**，但考虑将冷却和消耗做成可选特性：

1. **保留 ActiveAbility 和 PassiveAbility**（类型安全、易于理解）
2. **将冷却和消耗做成可选特性**（CooldownFeature、CostFeature）
3. **如果配置了特性，使用特性；否则使用内嵌属性**（向后兼容）

### 中期（6-12个月）

**评估完全组合模式**：

1. **创建原型**：实现完全组合模式的原型
2. **对比测试**：对比两种模式的开发效率和灵活性
3. **用户反馈**：收集插件用户的使用反馈

### 长期（1-2年）

**根据反馈决定**：

- 如果完全组合模式确实更灵活且用户接受度高，则完全迁移
- 如果混合模式已经足够，则保持现状

## 具体建议

### 关于冷却和消耗特性

**建议：做成可选特性，但保留内嵌属性**

理由：
1. **向后兼容**：现有技能无需修改
2. **灵活性**：可以选择使用特性或内嵌属性
3. **渐进迁移**：可以逐步迁移

实现方式：
```gdscript
class_name ActiveAbility extends GameplayAbility
    # 内嵌属性（向后兼容）
    @export var cooldown_duration: float = 0.0
    @export var costs: Array[AbilityCostBase] = []
    
    # 特性系统
    @export var features: Array[AbilityFeature] = []
    
    # 获取冷却时间（优先使用特性）
    func get_cooldown_duration() -> float:
        for feature in features:
            if feature is CooldownFeature:
                return (feature as CooldownFeature).cooldown_duration
        return cooldown_duration
```

### 关于主动/被动技能特性

**建议：暂时不采用完全组合模式**

理由：
1. **类型安全**：ActiveAbility 和 PassiveAbility 提供编译时类型检查
2. **概念清晰**：主动/被动是核心概念，不应该被特性化
3. **学习曲线**：完全组合模式对新手不友好

但如果确实需要，可以考虑：
- **保留类型**：ActiveAbility 和 PassiveAbility 仍然存在
- **内部实现**：它们内部使用 ActiveFeature 和 PassiveFeature
- **用户接口**：用户仍然使用 ActiveAbility 和 PassiveAbility

---

## 结论

### 推荐方案：渐进式组合

1. **保持 ActiveAbility 和 PassiveAbility**（核心类型）
2. **将冷却和消耗做成可选特性**（CooldownFeature、CostFeature）
3. **保留内嵌属性**（向后兼容）
4. **逐步迁移**：新技能使用特性，旧技能保持现状

### 不推荐：完全组合模式（当前阶段）

理由：
1. **过度设计**：对于大多数用例，混合模式已经足够
2. **类型安全**：完全组合模式会降低类型安全
3. **学习曲线**：对新手不友好
4. **迁移成本**：需要重写大量现有代码

### 未来考虑

如果确实需要更高的灵活性（如"被动技能+冷却时间"），可以考虑：
1. **创建原型**：实现完全组合模式的原型
2. **对比测试**：评估实际效果
3. **用户反馈**：收集使用反馈
4. **逐步迁移**：如果反馈良好，再考虑完全迁移
